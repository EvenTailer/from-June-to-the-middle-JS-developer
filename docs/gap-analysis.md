# Gap analysis: чего не хватает «JS → Middle», чтобы учить мидла, а не синтаксис

Дата: 2026-10-20. Метод: чтение исходников (`src/pages`, `src/widgets`, `src/entities`,
`src/shared/content`, `src/shared/store`), прогон `node scripts/validate-content.mjs`,
сверка с `docs/backlog.md` и `docs/textbook-plan.md`. Приложение не запускалось в браузере
(браузер в сессии не подключён), все выводы сделаны по коду.

---

## 1. Кто сейчас учится с этим приложением

Джуна с 0–1.5 годами опыта, который уже пишет на JS/React, но боится слова «middle» в вакансии.
Он читает 105 глав (549 секций, 141 941 слово прозы, в среднем 259 слов на секцию) — это плотность
хорошего курса, а не справочника.
Знание он проверяет честно: 610 вопросов теста в 62 блоках по 10 с разбором каждого ответа — это
единственный автопроверяемый слой в приложении.
Работу он не проверяет вообще: 502 задачи практики (уровень размечен у 469: 156 basic /
150 intermediate / 163 advanced), у каждой есть бриф, подсказка (478), эталонное решение и
объяснение (502) — но нет поля для ввода кода и нет исполнения кода. `validate-content.mjs` проверяет,
что решение существует и что в нём ≥ 3 строки, и всё.
Приложение обещает «задачи на код» (собственная строка `practice.blocks.stats`: «tasks to write» /
«задач на код»), но единственный способ «решить» задачу — нажать «Отметить решённой».
Прогресс, который он видит, на 85% состоит из самоотметок: `completedLessons`, `readChapters`,
`completedTasks`. Автоматически проверяются только 15% (тест).
Отдельный факт про зрелость продукта: главный показатель («92% пройдено») неотличим от «92% прокликал».

## 2. Где продукт заканчивается

| Ученик может | Ученик не может | Чем это закрывается сейчас |
| --- | --- | --- |
| Прочитать объяснение механизма и понять, почему оно ломается (105 глав, 549 секций) | Применить механизм к своей задаче и убедиться, что получилось | Ничем: `TaskCollection.tsx` рисует `CodeBlock` (read-only `<pre>`) и кнопку «Отметить решённой» |
| Ответить на 610 вопросов теста и получить вердикт + объяснение | Проверить свой код хотя бы на одном примере | Ничем: во всём `src` нет ни `textarea`, ни `iframe`, ни `sandbox`, ни `postMessage`, ни `new Function`, ни `Worker`, ни редакторской зависимости в `package.json` |
| Пройти 502 задачи как структурированный чек-лист тем | Отличить своё решение от эталона | Ничем: `completedTasks.push(id)` в `progressSlice.ts` |
| Знать, что писать (бриф с явными контрактами: «`slugify("Hello, World!")` возвращает `"hello-world"`») | Знать, выполняет ли его код этот контракт | Ничем: контракт живёт прозой в брифе, поля для проверки нет |
| Изучить теорию code review, ADR, фичефлагов, ретраев, идемпотентности (git-ch5/ch6, architecture-ch5/ch7) | Сделать хотя бы один настоящий code review, написать ADR, включить фичефлаг | Ничем: все 502 задачи построены по схеме «напиши с нуля», ни одна не про командную работу |
| Написать тест на vitest в рамках задания (тема `testing`, 8 задач) | Запустить этот тест | Ничем: в приложении нет ни vitest, ни раннера, ни кнопки «Run» |
| Понять протокол HTTP, кэш, CORS, auth (9 глав) | Поднять endpoint, написать серверный обработчик | Ничем: http-модуль — это протокол со стороны клиента; Node/сервера в продукте нет вообще |
| Изучить 12 модулей | Перенести знание в новую, непохожую задачу | Ничем: тест проверяет память, а не перенос; сквозного проекта нет |
| Написать пример из 10–22 строк из главы | Поработать с кодовой базой > 1000 строк | Ничем: правило `docs/textbook-plan.md` (строка 41) ограничивает образец 10–22 строками |
| Отметить 105 глав прочитанными | Получить оценку уровня, которую можно показать ментору | Ничем: 85% прогресса — самоотчёт, хранится в `localStorage` (`js-tutorial:state:v1`), не выгружается и не проверяется |

## 3. Разрывы

### R1. Обратной связи по коду ученика нет в принципе

**Что за разрыв.** Приложение требует писать код, но нигде не даёт места для кода и нигде его не
исполняет. Подтверждено чтением исходников: `TaskCollection.tsx` (строки 223–234) рендерит
`<CodeBlock code={task.solution} />` — это статический блок; ни одного элемента ввода в `src` нет;
зависимостей-редакторов нет. Проверка знания работает (тест с 4 вариантами), проверка работы — нет.
**Кто страдает.** Все, но в первую очередь те, кто тратит на задачу 20–40 минут вне приложения и
возвращается, чтобы нажать кнопку; и менторы, которым нужен сигнал об уровне ученика.
**Стоимость.** M, если делать эшелонированно (ниже). L, если реализовать B1 буквально.

**Гипотеза подтверждена — но B1 покрывает только её меньшую часть.**

Что B1 закрывает: запуск кода в sandbox-iframe с `postMessage` и показ упавших кейсов.
Что B1 не закрывает:
1. **Покрытие.** Исполняемы в браузере примерно 90–110 задач из 502 (18–22%): чистые функции из
   тем `algorithms`, `arrays`, `strings`, `numbers`, `objects`, `functions`, `loops`, `types`,
   `errors`, `oop`, `async` (по 8 задач на тему). Остальные — React-компоненты (4 темы × 8 = 32),
   CSS-правила, команды git и shell, HTTP-запросы, задачи по архитектуре. Их в браузере не запустить.
   То есть «задачи без тестов остаются read-only» (пункт DoD B1) — это не исключение, а ~78% задач.
2. **Качество эталона.** Сегодня ни одно эталонное решение не проверено машинно:
   `scripts/validate-content.mjs` (строки 439–444) проверяет наличие `solution` и длину в 3 строки.
   То, что ученик копирует как «правильный ответ», может не работать. B6 покрывает только
   `code` из глав, задачи — нет.
3. **Обратная связь вне кода.** CSS, git, shell, HTTP, ADR — половина практики — не исполняется
   никогда, и для них нет даже схемы проверки «кроме как посмотреть на эталон».

**Риски, если делать исполнение.**
- *Безопасность.* Код ученика не должен исполняться в realm приложения. Рабочая схема: iframe с
  `sandbox="allow-scripts"` и **без** `allow-same-origin` (непрозрачный origin — нет доступа к DOM
  родителя, к `localStorage` и к cookie), внутри iframe код выполняется в Web Worker, таймаут с
  `terminate`, лимит размера кода. Остаточные риски: iframe всё ещё может уйти в сеть (`fetch` уйдёт,
  тело не прочитает из-за CORS) — нужен CSP внутри фрейма `default-src 'none'`; бесконечный цикл в
  воркере съедает ядро до срабатывания таймаута.
- *Стоимость.* Авторские тесты для 502 задач — нереалистично; даже 100 задач — это отдельный
  контентный проект того же масштаба, что текущая переработка учебника (141 941 слово). Плюс каждой
  задаче нужен «контракт», который сейчас существует только словами в брифе.
- *Бандл.* Monaco добавит 3–5 МБ и убьёт цель B4 (2 МБ → <700 кБ). Разумная альтернатива —
  `<textarea>` с моноширинным шрифтом (0 КБ) или CodeMirror 6, подгружаемый лениво при первом
  открытии задачи.
- *Отказ от своего раннера.* Кнопка «открыть в CodeSandbox/StackBlitz с предзаполненным кодом»:
  ноль рисков для нашего домена, но ученик уходит из продукта, прогресс не возвращается, офлайн
  не работает.

**Дешевле и с заметно бо́льшим покрытием — эшелонированная схема:**

| Уровень | Что проверяет | Покрытие | Стоимость |
| --- | --- | --- | --- |
| L0 «предскажи вывод» | ученик вводит результат, сверка с эталонным значением из контента | ~350 задач с однозначным выводом | S: поле `expected` в задаче + поле ввода + сравнение |
| L1 «чек-лист контракта» | 3–5 проверяемых утверждений, вытащенных из брифа, + место для кода рядом | все 502 | S: разметка брифа + чекбоксы |
| L2 «парсится / типы / линт» | «код парсится», «типы сходятся», «линтер чист» | ~250 (js + ts + react) | M: `oxlint`/TypeScript в воркере, лениво |
| L3 «исполнение в sandbox + тесты» | настоящие кейсы | 90–110 | M–L |
| L4 «экспорт во внешний IDE» | полноценная среда | все 502 | S: кнопка + шаблон |

По ценности на единицу усилий порядок L0 → L1 → L2 → L3: первые два уровня дают обратную связь
примерно на 70% задач и вообще не требуют исполнения чужого кода.
**Связь с бэклогом.** B1 покрывает только L3 и только для задач с тестами. L0, L1, L2 — новое.

### R2. Прогресс измеряет активность, а не навык

**Что за разрыв.** Четыре поля `ProgressState`: `completedLessons`, `readChapters`,
`completedTasks` — самоотметка; `quizScores` — единственная автопроверка. Веса
(`HomePage.tsx` 102–104, `ModulePage.tsx` 212–214): 15% вопросы + 35% учебник + 50% практика.
Итог: 85% показателя — «я нажал кнопку», 15% — «я ответил правильно». Практика при этом весит
больше всех вместе взятых, а проверяется нулём.
**Кто страдает.** Ученик — потому что «92%» он прочитает как «я готов к собеседованию»; ментор и
владелец продукта — потому что показатель нельзя использовать как доказательство.
**Стоимость.** S (перевесить: 15% автопроверенный тест, 15% исполненная практика, 70% прочитано,
и подписать каждую метку как «самооценка») + M, если вводить отдельную метку «пройдено исполнением».
**Связь с бэклогом.** Не покрыто. B10 добавляет счётчик глав в hero, формулу не трогает.

### R3. В приложении две разные формулы прогресса

**Что за разрыв.** `Header.tsx` (18–22) считает 20% вопросы + 80% задачи. `HomePage.tsx` (102–104)
и `ModulePage.tsx` (212–214) — 15% / 35% / 50%. Оба числа называются «прогресс» и видны рядом.
**Кто страдает.** Ученик, который сравнивает процент в шапке с процентом на главной.
**Стоимость.** S. **Связь с бэклогом.** Не покрыто.

### R4. Нет ни одного задания, где ученик читает или ревьюит чужой код

**Что за разрыв.** Все 502 задачи построены по одной схеме: бриф → подсказка → эталон → объяснение,
то есть «напиши с нуля». Нет задачи «вот код, найди баг», нет «вот дифф, напиши ревью», нет
«доделай чужую функцию». Между тем работа мидла — это в основном чтение чужого кода, рефакторинг
и разбор существующей системы, а не написание с нуля.
**Кто страдает.** Именно тот, кто идёт в мидл: на собеседовании его просят читать чужой код.
**Стоимость.** M — нужен новый формат задачи (`given` / `brokenCode` / `findings`) и автопроверка
формата «нашёл N из 3 мест» (список дефектов в контенте).
**Связь с бэклогом.** Новое.

### R5. Нет сквозного проекта

**Что за разрыв.** 105 глав изолированы: ни одна не продолжает предыдущую, единого репозитория,
который растёт от главы к главе, нет. Максимум «как это в реальном проекте» — фрагмент на 10–22
строки внутри секции (правило `docs/textbook-plan.md`, строка 41). Ни разу за 549 секций не
показано, как 20 кусков складываются в один работающий фичер с ревью, тестами и релизом.
**Кто страдает.** Ученик на переходе от «решаю задачки» к «работаю в проекте»: у него нет
референса целиком, и он не знает, какой минимальный набор решений принимают в реальном фиче.
**Стоимость.** L (новый слой контента: сквозной пример + перекрёстные ссылки из глав).
**Связь с бэклогом.** Новое.

### R6. Нет модуля «Тестирование»

**Что за разрыв.** Тема `testing` — это 8 задач. Разбросанные секции: `react-ch11` (тестирование
компонентов), `redux-ch7` (тестирование слайсов и селекторов), `router-ch7` (тесты роутера).
Нет: конфигурации vitest, `setup`-файла, fake timers, MSW, e2e (Playwright/Cypress), пирамиды
тестов, что покрывать и что не покрывать, flaky-тестов, coverage-гейта в CI, контрактных тестов.
Для middle это навык №1 и самая частая тема собеседований.
**Кто страдает.** Все, кто идёт дальше джуна; и те, кто приходит с «я умею писать тесты» —
потому что проверить это в приложении нечем.
**Стоимость.** L (7–8 глав + ~60 задач). **Связь с бэклогом.** Новое.

### R7. Нет Node.js и серверной разработки

**Что за разрыв.** Все 12 модулей фронтендовые. http-модуль (9 глав) учит протокол со стороны
клиента: заголовки, кэш, TLS, CORS, auth, проектирование API. Ни одной задачи «поднять endpoint»
в продукте нет; тема `http` — 8 задач; `cli-ch7` учит ходить в БД по ssh и curl, то есть читать,
а не разрабатывать. На рынке middle JS почти всегда full-stack, и приложение честно заканчивается
на «я умею делать интерфейс».
**Кто страдает.** Кто ищет позицию full-stack и упирается в пробел именно там.
**Стоимость.** L (новый модуль) — либо честная отсылка наружу (см. раздел 4).
**Связь с бэклогом.** Новое.

### R8. Нет практики командного и продуктового цикла

**Что за разрыв.** Теория есть и хорошая: `git-ch5` (fetch/push, force-with-lease, worktrees),
`git-ch6` (PR, semver, changelog, hotfix), `architecture-ch5` (фичефлаги, логи, outbox, ретраи,
circuit breaker, кэш-стампид), `architecture-ch7` (ADR, качественные атрибуты, эволюция вместо
переписывания). Но ни одна из 502 задач к этому не относится: все они — «напиши функцию,
компонент или правило». Нет задачи «добавь фичефлаг и его owner», «напиши ADR под это решение»,
«разбери hotfix-дифф», «ответь на ревью».
**Кто страдает.** Тот, кому предстоит первая работа в команде: он знает слова, но не проходил цикл.
**Стоимость.** M (переформатировать существующие теории в задачи формата ADR / diff-review / flag).
**Связь с бэклогом.** Новое.

### R9. Эталонные решения задач не проверены машинно

**Что за разрыв.** `validate-content.mjs` (439–444) проверяет наличие `solution` и ≥ 3 строк в ней.
Ни парсинга, ни запуска, ни сверки вывода с текстом объяснения. То есть «эталон» — это текст,
а не проверенный код, и ученик, скопировавший его, мог скопировать нерабочее. Отдельно: в репозитории
живут 4 предупреждения валидатора (3× ru/en word ratio в `js-core/ch05, ch09, ch10`, 1× решение
короче 3 строк в `topic-cli-1`) — то есть в текущем состоянии валидатор проходит, но с 4 предупреждениями.
**Кто страдает.** Ученик, который копирует решение и получает неверный результат; и автор
контента, у которого нет защиты от такой ошибки.
**Стоимость.** S (парсинг через `esbuild`/`oxlint` — это же уровень L2 из R1), M (запуск чистых
функций и сверка с `expected`).
**Связь с бэклогом.** B6 покрывает только учебник; по задачам не покрыто.

### R10. Нет связи «практика ↔ теория» в интерфейсе

**Что за разрыв.** `chapterId` проставлен у 105 задач (по одной на главу) и не показывается нигде.
Из главы нельзя перейти к её задачам, из задачи — к главе. Для 105-главного учебника это
самая дешёвая недостающая связь, и она уже лежит в данных.
**Кто страдает.** Ученик, который читает главу и не получает «тренируй это здесь».
**Стоимость.** S. **Связь с бэклогом.** B9 покрывает ровно это — уже в бэклоге, реализовывать не надо.

### R11. Контентные пробелы уровня middle

| Тема | Что есть | Чего нет | Оценка |
| --- | --- | --- | --- |
| Безопасность | 8 задач темы `security` + `http-ch5/ch6` | OWASP Top 10, IDOR/BOLA, `npm audit`, авторинг CSP, секреты в CI, OIDC flows в деталях | M (модуль) |
| Производительность в проде | `react-ch10` (memo, виртуализация), `next-ch8` (размер бандла) | Core Web Vitals (LCP/INP/CLS), чтение waterfall, профилировщик, бюджет бандла как проверка в CI | M |
| Отладка и профилирование | `js-core-ch12` (5 секций про try/catch и стектрейсы) | DevTools-профилировщик, flame chart, утечки памяти, detached DOM, «сломалось только в проде» | M |
| Локализация | `js-core-ch10` — раздел про Intl | i18n-каталоги, RTL, плюрали, форматирование в UI, переключение локали без перезагрузки | S–M |
| Дизайн-системы | `htmlcss-ch5/ch6/ch7` (каскад, flex, grid) | токены, темы, Storybook, версионирование компонентов, contribution-процесс | M |
| Реальное время и API | `http` упоминает WebSocket, `next-ch4` — server actions | GraphQL, клиентский retry/backoff, оптимистичные апдейты, websocket-приложение целиком | M |
| Монорепо и воркспейсы | 1 секция `cli-ch8` + 1 `git-ch7` | монорепо целиком: workspace-протокол, turbo/nx, зависимости между пакетами | M |
| Доступность в реальном продукте | `htmlcss-ch3` — 6 сильных секций | скринридер-тестирование, аудит легаси, WCAG 2.2 / EN 301 549 / №152-ФЗ как требование, приоритизация в бэклоге | M (в основном отсылка) |
| LLM/AI-интеграция | ничего | нет ни слова про интеграцию с LLM-API — в 2026 это часть многих middle-вакансий | S–M |

**Кто страдает.** Все, кто доучивает до middle: пробелы не в синтаксисе, а в том, что определяет
уровень. **Стоимость.** L суммарно (это набор, а не один пункт). Внутренний приоритет:
безопасность → производительность/наблюдаемость → тестирование (R6) → Node (R7).
**Связь с бэклогом.** Не покрыто ни одним из B1–B10.

### R12. Приложение не признаёт своих границ

**Что за разрыв.** Ни на одной странице нет блока «это учебник, а не симулятор работы»: ни в hero,
ни в конце модуля, ни в тренажёре, ни в футере. Ученик узнаёт о своих границах не от приложения,
а от первой же рабочей задачи.
**Кто страдает.** Выпускник: он не знает, чего ему не хватает, и тратит месяц на то, чтобы понять,
что нужен тикет, а не учебник.
**Стоимость.** S (страница «Что дальше», 2–3 честных абзаца на модуль, 6–8 ссылок наружу).
**Связь с бэклогом.** Новое.

## 4. Честные границы учебника

Что приложение принципиально не может научить и должно признать (с указанием, куда отсылать):

1. **Работа в команде и code review как социальная практика.** Приложение научит читать дифф и
   писать ADR, но не даст опыта «получил замечания старшего коллеги, отвечаю, спорю, отступаю».
   → Отсылка: открытый PR в чужом small-проекте, работа в репозитории с живыми людьми.
2. **Прод-инциденты и дежурства.** `architecture-ch5` и `http-ch9` дают инструментарий (идемпотентность,
   ретраи, circuit breaker, tracing, метрики), но не дадут «в 3 часа ночи падает прод».
   → Отсылка: первый год on-call, открытые постмортемы, deliberately broken сервисы.
3. **Требования бизнеса, приёмка, оценка сроков.** `architecture-ch7` учит фиксировать решение
   (ADR) и формулировать качественные атрибуты, но не учит выяснять у бизнеса, что именно нужно.
   → Отсылка: работа в продуктовой команде, чтение реальных тикетов и критериев приёмки.
4. **Доступность в реальном продукте.** `htmlcss-ch3` силён технически, но не покрывает
   скринридер-тестирование, аудит легаси и юридические требования (WCAG 2.2 AA, EN 301 549,
   №152-ФЗ, ADA) — а именно они определяют объём работы.
   → Отсылка: axe DevTools, ручные прогоны VoiceOver/NVDA, аудит чужого публичного сайта.
5. **Миграции и техдолг.** Приложение не научит переводить jQuery-монолит на React по шагам и не
   научит продавать рефакторинг. `architecture-ch7` говорит «эволюция, а не переписывание», но
   без практики переноса.
   → Отсылка: миграция в реальном проекте, Strangler Fig на своём легаси.
6. **Комплаенс и юридические рамки.** Техническая база (http-ch5, http-ch6) есть; политики компании
   (GDPR, PCI, хранение ПДн, согласия на cookies) — нет и не может быть.
   → Отсылка: политика работодателя, отраслевые нормы, DPO.
7. **Поиск работы и самопродажа.** Резюме, собеседования, system design, переговоры о зарплате.
   Ни один модуль об этом не может быть честным — учебник не должен притворяться.
   → Отсылка: разбор вакансий, mock-интервью, курсы по system design.
8. **Работа с большой чужой кодовой базой.** Все 549 секций дают маленькие автономные куски.
   Навык «войти в незнакомый репозиторий на 200k строк» тренируется только в реальном репозитории.
   → Отсылка: чтение чужого кода, первая неделя в новом проекте.
9. **Этика и приоритеты в конфликте.** Что делать, когда просят задеплоить сломанное, когда чинить
   баг «не в скоупе», как спорить со сеньором.
   → Отсылка: работа с наставником, culture/code-of-conduct компании.
10. **Поведение на реальных объёмах и данных.** Перфоманс на синтетике не равен перфомансу на
   продакшен-трафике.
   → Отсылка: RUM-мониторинг в работе, профилирование реального приложения.

Что приложение обязано компенсировать и может: безопасное место, где можно ошибиться; структурную
обратную связь по знанию (тест с разбором); список «на что смотреть» (чек-листы, callouts, pitfalls);
словарь и быстрый поиск по тому, что ты знаешь; воспроизводимый тренажёр тем.
Это сильные стороны продукта — в отчёте они должны быть названы, а не потеряны за списком пробелов.

## 5. Пять самых ценных следующих шагов

1. **Дать обратную связь там, где она дешёвая: L0 «предскажи вывод» + L1 «чек-лист контракта»
   на все 502 задачи.** Новое (B1 покрывает только L3). Почему первое: покрытие ~70% практики
   без единого выполнения чужого кода, без sandbox, без новых зависимостей и без риска для
   безопасности; данные (`brief` с явными контрактами) уже есть, нужен только разбор брифа на
   3–5 проверяемых утверждений и одно поле `expected`. Стоимость S. Побочный эффект: исчезает
   главный источник жалоб — «я отметил решённой, но не знаю, правильно ли».
2. **Довести до конца исполнение там, где оно возможно: sandbox-iframe + Worker + таймаут и
   автотесты для 90–110 чистых задач.** B1 (частично — нужен ещё `expected`-контракт, проверка
   эталона и решение по безопасности: `sandbox` без `allow-same-origin`, CSP `default-src 'none'`
   внутри фрейма, terminate по таймауту). Почему второе, а не первое: это единственный способ
   дать настоящий сигнал «твой код неверен», но покрытие ограничено примерно пятой частью
   практики, а разработка — M–L. Делать вторым после L0/L1, когда уже видно, какие задачи
   тестируемые, и не тащить Monaco (3–5 МБ) — взять `<textarea>` или ленивый CodeMirror,
   чтобы не конфликтовать с B4.
3. **Перестать измерять клики: разделить «прочитано / изучено» (самооценка) и «проверено»
   (тест, исполненная практика), пересчитать веса и починить две разные формулы.** Новое
   (B10 — только счётчик глав в hero). Почему третье: 85% текущего прогресса — самоотчёт, и это
   главный показатель продукта; пока он не отражает навык, его нельзя показать ментору и нельзя
   использовать для оценки курса. Стоимость S–M. Внутри: одна формула вместо двух (R3),
   подписи меток «самооценка», вес 50% у практики заменяется на вес исполненной практики.
4. **Добавить два формата, которых у мидла нет больше всего: задания на чтение/ревью чужого кода
   и первый сквозной проект.** Новое. Почему четвёртое: все 502 задачи сегодня — «напиши с нуля»,
   а 60–70% работы мидла — чтение чужого кода, рефакторинг и разбор диффа; сквозной проект
   закрывает главный разрыв «учебник учит синтаксису, а не тому, как устроена работа»
   (R4 + R5). Стоимость M (формат задачи) и L (сквозной проект) — поэтому начать с формата
   «что-то сломалось — найди», он дешевле и учит тому же.
5. **Закрыть два самых заметных пробела в содержании: модуль «Тестирование» (7–8 глав) и
   серверный/Node-раздел.** Новое. Почему пятое: тестирование — навык №1 и тема №1 собеседований,
   а сейчас это 8 задач и разбросанные секции; Node нужен, потому что все 12 модулей фронтендовые,
   и приложение честно заканчивается на «я умею делать интерфейс». Стоимость L на оба; если
   ресурса нет — начинать с тестирования, оно усиливает и существующие модули (react, redux,
   react-router, next), и даёт честный шанс закрыть R1: тест на vitest — это и есть проверяемый
   контракт, который можно положить в `tests` для B1.

Заведённые ранее B2, B3, B5, B7, B8, B9, B10 остаются в силе и не конфликтуют с этим списком.
B4 (2 МБ → <700 кБ) становится обязательным precondition для шага 2: раннер и редактор не должны
попасть в entry-чанк. B6 стоит расширить на решения задач (R9) — иначе «эталон», который ученик
копирует, остаётся непроверенным текстом.
