# Backlog

Open work for the tutorial. The team lead triages this list, orders it by
dependency and delegates it to workers. New findings from the critic are
appended here with the same shape.

Each item carries a definition of done that a worker can check without asking.

The order below is the order of work: an item sits after everything it reads
or changes. The waves say what can run in parallel without two workers
touching the same file.

The gaps of the product that the backlog does not cover yet come from
`docs/gap-analysis.md` (the analyst) and from `docs/critic-reports/` (the
critic). They are in the waves below under R and C.

## Wave 1 (Волна 1)

Wave 1 is the foundation: the bundle no longer carries the content, the build
refuses broken content and the plan document stops promising something the
code does not do. B4 and B5 are done. The two briefs below are ready to run
and touch files nobody else touches.

### B6a. The samples of the textbook are parsed

A code block can claim an output the code does not produce, and nothing
catches it. The textbook has 549 samples and 149 of them are not JavaScript
at all, so the check has to know the language of every sample.

- `ChapterSection` in `src/entities/module/model/types.ts` gains an optional
  `lang?: 'js' | 'ts' | 'jsx' | 'html' | 'css' | 'shell' | 'sql' | 'json'`.
  The default is `js`.
- `scripts/validate-content.mjs` parses every `code` field of every section
  and reports an error when the sample does not parse. The parser is the one
  TypeScript already ships: `ts.transpileModule(code, { reportDiagnostics:
  true })`, and only diagnostics of category `Error` count. `typescript` is
  already a devDependency, so no new package is needed.
- The 149 non JavaScript samples are tagged. They sit in 34 files:

  | Module | Samples | Files |
  | --- | --- | --- |
  | cli | 43 | `chapters/cli/ch01.ts` … `ch08.ts` (8) |
  | git | 38 | `chapters/git/ch01.ts` … `ch07.ts` (7) |
  | html-css | 42 | `chapters/htmlCss/ch01.ts` … `ch08.ts` (8) |
  | http | 17 | `chapters/http/ch01.ts` … `ch05.ts` (5) |
  | nextjs | 1 | `chapters/nextjs/ch09.ts` |
  | react-router | 4 | `chapters/reactRouter/ch01.ts`, `ch03.ts`, `ch04.ts` |
  | redux | 1 | `chapters/redux/ch05.ts` |
  | typescript | 3 | `chapters/typescript/ch09.ts` |

  The cli, git and http samples are shell, the html-css ones are HTML, the
  nextjs one is SQL, the react-router ones are JSON and JSX, the redux one is
  TypeScript and the typescript ones are JSON.
- The check also catches the samples of a chapter that is written in a
  language it does not claim, so `lang` becomes a promise the validator
  keeps.

Done when a sample that does not parse makes `npm run validate:content` fail,
and the 400 JavaScript samples still pass.

### B7. The plan document describes the current state

`docs/textbook-plan.md` was written as a target. It still says "Target
structure", still explains "Why the rewrite", still carries the "Chapters
before" column, and its section counts (488) are the ones the rewrite aimed
for. The code has 105 chapters and 549 sections.

- Rewrite the document as a description of what exists: one chapter per
  practical topic, the section format, the rules the writing follows, the
  numbers the code has now.
- Take the numbers from the code, not from the old table. The chapter counts
  are in `src/shared/content/chapters/index.ts` (`chapterCountByModule`), the
  section counts are what `npm run validate:content` prints.
- The "Quiz blocks" column describes the blocks that exist today, five or six
  per module. B2 replaces them with one block per chapter, so that column is
  the only part of the document B2 has to touch later.
- Keep the document short: it is a description of the textbook for the people
  who write the next chapter, not a history of the rewrite.

Done when every number in the document is the number in the code and the
document reads as a description, not as a plan.

### B1a. Run the code of a learner

The practice tab shows the exemplar solution. Nothing lets a learner submit
their own code and find out whether it works.

- A code editor next to the solution, prefilled with the exemplar.
- `PracticeTask` gains an optional `tests` field: an array of
  `{ input, expected }` pairs, or a single `test` source string that runs
  against the learner's code.
- The check runs in a sandboxed iframe with `postMessage`; the page never
  evaluates learner code in the main realm. The iframe needs `sandbox="allow-scripts"`
  without `allow-same-origin`.
- The result lists the cases that failed, with the expected and the actual
  value.
- A task without tests keeps the current read-only behaviour.
- Pilot: the chapter tasks of one module carry the tests, the other modules
  keep the read-only behaviour.

Done when a learner can write code, run it and see which cases fail.

### B1b. Tests for every chapter task

The 105 chapter tasks of `src/shared/content/tasks/chapters/*.ts` get the
tests B1a introduced. One task per chapter, one or two cases each, the case
that fails for the wrong reason first.

Done when every chapter task has at least one case and a learner who solved
the task passes it.

### B2. One quiz block per chapter

`quizBlockTitles` in `src/shared/content/quizBlocks.ts` lists five or six
fixed titles per module while the module now has seven to fourteen chapters.

- One quiz block per chapter, titled with the chapter title.
- The block count follows the chapter count.
- Questions stay where they are; only the grouping and the titles change.
- The chapter titles come from the textbook, so the generator
  `scripts/generate-module-index.mjs` has to publish them. It already reads
  the module files, so it can read `src/shared/content/chapters/<module>/chNN.ts`
  the same way and write a `chapterTitleById` map next to `lessonModuleById`.
- The counts of the blocks are no longer a function of the question count, so
  `quizBlockMeta` in `src/shared/content/quizBlocks.ts` has to change with it.

Done when the quiz tab shows one block per chapter and the titles match.

### B10. The module page shows the textbook progress

- Show the chapters read next to the other two counters. The numbers are

### B3a. The questions layer shrinks

`lessons` holds forty to ninety question cards per module that overlap heavily
with the new chapters. The four tabs have to say four different things.

- Decide between shrinking `lessons` to the fifteen to twenty questions that
  carry the most value and folding the questions into the sections.
- Shrink the questions of two modules first (`js-core` with ninety lessons and
  `react` with eighty) and measure what the layer looks like afterwards.
- The lesson ids of the questions that stay must not change, the progress of
  a learner who already read a question must not be lost.
- After the content changed, run `npm run generate:module-index`: the counts
  and the lesson to module map are generated.

Done when the questions layer of the two pilot modules carries only what the
chapters do not.

### B9. The chapter a task drills is visible

`PracticeTask.chapterId` is set but never shown.

- The practice card links to the chapter it belongs to.
- The theory tab links back to the tasks of the chapter.
- The chapters load on demand, so the title of a chapter has to be available
  without loading the chapter. B2 publishes the titles in the generated module
  index, use them.
- The task ids the theory tab links to need an anchor. The task card has no
  `id` today, add `id={`task-${task.id}`}`.
- The chapter the practice tab links to is behind a lazy load, so the jump
  has to wait for the chapter to exist. `ModuleTheory` owns the scroll, the
  link must not land on a missing element.

Done when a learner can move between a chapter and its task in both
directions.

### B8a. One search field in the header

Each tab has its own search, or none. The theory tab has one, the questions
tab has one, the practice tab has none.

- One search field in the header that searches the modules and the chapters.
- Results grouped by kind, each result links to where it lives.
- The chapters are a lazy chunk per module, so the search has to load the
  chapters of the modules it has to look into. Show that it is searching.

Done when a search for a term finds the module and the chapter that mention
it.

## Findings from the critic

The critic reads the content and reports, it does not rewrite. The two reports
in `docs/critic-reports/` are a snapshot from 2026-10-20. The working tree
already carries partial fixes, so every finding has to be checked against the
file as it is now before anything is changed. A finding that the current file
does not have is closed, not fixed twice.

### C1. The chapter tasks carry 54 defects

Report: `docs/critic-reports/tasks.md`. Nineteen blocking, twenty-eight
shaping, seven polish, all of them in the `solution` strings, which is why
`tsc` and the validator never saw them.

- The nineteen blocking findings are the ones that matter: a solution that does
  not compile (`chapters/typescript.ts:156`, `chapters/redux.ts:145`,
  `chapters/reactRouter.ts:189`, `chapters/nextjs.ts:63`), a solution that
  does not do what the brief asks (`chapters/http.ts:363`,
  `chapters/architecture.ts:266`, `chapters/react.ts:464`), and a solution
  that teaches the wrong thing (`chapters/cli.ts:133`, `chapters/oop.ts:240`).
- The work splits by file: `src/shared/content/tasks/chapters/<module>.ts`.
  One worker per module, no file is touched by two workers.
- The machine check for this item exists: `scripts/check-task-solutions.mjs`
  compiles every solution under strict and reports the ones that fail. It has
  to be green before the item is closed, and it belongs in the build next to
  the content validator.

Done when every blocking finding of the report is closed or the finding does
not exist in the current file, and the blocking findings of the other modules
have the same fate.
